Cada pitufo es una carpeta en `src/mastra/agents/` (su persona) y, si actúa sobre un repo, un workflow en `src/mastra/workflows/` (clonar → correr el agente → commit → PR). Todos se registran en `src/mastra/index.ts` (`CLAUDE.md`, sección «Adding a new smurf»).

<Info>
  **LIVE** = cableado de punta a punta y programado (o activado por evento). **stub/off** = estructura y persona correctas, pero la acción no está cableada ni activada. Los pitufos de evento están **INERTES** hasta que su secreto correspondiente está puesto (ver [Webhooks](/sistemas/vivla-smurfs/webhooks)).
</Info>

## Pitufos de código (Claude Agent SDK)

Corren dentro de un clon del repo objetivo. El modelo por defecto es **opus** (`claude-opus-4-8`) salvo que se indique (`src/config/models.ts:23`).

| Pitufo | Fichero | Qué hace | Estado |
|---|---|---|---|
| **Architect** | `architect.ts` | Un módulo → pase de mejora coherente (lote de ~3-6 mejoras relacionadas, skills de Pocock) → PR borrador | LIVE |
| **Painter** | `painter.ts` | Una superficie de frontend web → pase de pulido visual → PR borrador | LIVE |
| **Vanity** | `vanity.ts` | Una ruta pública de un sitio → pase de SEO / accesibilidad / peso → PR borrador. Solo repos con `webRoutes` | LIVE (ver nota) |
| **Hefty** | `dep-steward.ts` | Barrido semanal de dependencias: cada patch/minor seguro + smoke → PR borrador | LIVE |
| **Nosey** | `migration-safety.ts` | Escanea migraciones (números duplicados / drift de snapshot) → **issue** (nunca PR, nunca edita migraciones) | LIVE |
| **Tailor** | `tailor.ts` | Un módulo → barrido de tipos (cada estrechamiento seguro, solo tipos) → PR borrador | LIVE |
| **Papa** | `papa.ts` | Un módulo (de la cola `docs/refactor-queue.md` del repo si existe) → refactor estructural que preserva comportamiento → PR borrador | LIVE |
| **Editor** | `wiki-sync.ts` | Sync diario del wiki MDX según el diff de `develop` + auditoría semanal de obsolescencia → PR borrador | LIVE |
| **Scribe** | `scribe.ts` | Sync diario de las reglas de negocio de vivla-api (leídas de `master`) hacia **docs** (wiki) y **vivla-atlas** | LIVE |
| **Documenter** | `documenter.ts` | Sync del wiki dirigido por el `repos.yml` del repo `docs`: documenta cada entrada `mode: documenter` bajo `sistemas/<repo>/` (**este pitufo escribe esta sección**) | LIVE (diff) |
| **Handy** | `sentry-fixer.ts` | Mejor issue de Sentry → arreglo (PR borrador) o veredicto → entrega a `triage()` de Postman; nunca escribe en Linear | LIVE |
| **Brainy** | `brainy.ts` | «Mano derecha» de Linear: un issue mencionado/delegado → un PLAN, una INVESTIGACIÓN de solo lectura, o un PR borrador | event-driven |
| **Grouchy** | `security-auditor.ts` | `npm audit` + barrido OWASP → issues | stub/off |
| **Guardian** | `supabase-security.ts` | Advisors de Supabase → PR borrador de migración correctiva | stub/off |

(Tabla derivada de `CLAUDE.md`, sección «Roster», y `src/mastra/index.ts:214`.)

<Note>
  **Scribe** es la excepción deliberada a la regla de dos objetivos: LEE un tercer repo, `vivla-api` (de otro equipo, estrictamente de solo lectura) y ESCRIBE en `docs` y `vivla-atlas`. Su PR al wiki es **la única excepción** a «la flota nunca mergea»: abre en estado READY y Scribe lo squash-mergea cuando pasa el *Wiki build check* (`tools/wiki-automerge.ts`) — el wiki es la fuente de verdad técnica y debe estar vivo (`CLAUDE.md`, sección Schedules). El Documenter aplica el mismo patrón para las secciones `sistemas/<repo>/`.
</Note>

## Pitufos de texto y de evento

Sin acceso a repo. Los `Agent` de Mastra van por el router de modelos (prefijo `anthropic/`); el código puro no llama a ningún modelo (`src/config/models.ts:34`).

| Pitufo | Fichero | Qué hace | Motor · modelo | Estado |
|---|---|---|---|---|
| **Poet** | `changelog-drafter.ts` | PRs mergeados → `CHANGELOG.md` → PR borrador | ClaudeSDKAgent · haiku | LIVE |
| **Reporter** | `reporter.ts` | Digest semanal de prensa: PRs/commits de la semana → Slack (producto + por repo) | Agent · `claude-opus-5` | LIVE |
| **Alma analyst** | `alma-analyst.ts` | Digest diario de actividad de Lola (métricas + commits) → Slack | Agent · haiku | LIVE |
| **Lola weekly analyst** | `lola-weekly-analyst.ts` | Análisis semanal (lunes 09:00) de los 7 días previos de Lola → informe interno | Agent · haiku | LIVE |
| **Lola watcher** | *(sin agente — `lola-watcher.ts`)* | Cada 2 min: avisa en Slack de mensajes nuevos / borradores en canales donde responde un agente | código puro | LIVE |
| **Postman** | `postman.ts` | **El pitufo cartero**: triaje de Product Requests en Slack → responde, deduplica, abre un issue de Linear con el hilo sincronizado, o pasa a Don Draper | Agent · opus | event-driven; SHADOW por defecto |
| **Iconero** | `src/icons/iconero.ts` | **El pitufo de los iconos**: dibuja iconos del set VIVLA para la Content Factory, con revisora independiente | ClaudeSDKAgent (`query()`) · `claude-opus-5-5` (`ICONERO_MODEL`) | event-driven |
| **Design** | *(sin agente — `design-intake.ts`)* | La puerta de Postman al equipo HOM: «Materiales de casas» → issue de HOM determinista | código puro | event-driven (mismo webhook que Postman) |
| **Brainy (triage stub)** | `triage-classifier.ts` | Enruta items a un pitufo (placeholder legado) | Agent · haiku | stub/off |

(Tabla derivada de `CLAUDE.md`, sección «Roster». Los detalles de triaje de Postman, el flujo de Brainy y el enrutado de Cursor viven en `CLAUDE.md`.)

<Tip>
  Cada pitufo tiene un lanzador one-shot en `runners/run-<nombre>.ts` para prueba manual o CI, que importa el `run*()` del workflow y lo ejecuta una vez sin el scheduler (p. ej. `pnpm handy`, `pnpm nightly:architect`, `pnpm sweep:sentry`) (`package.json`, `CLAUDE.md`, sección Runtime).
</Tip>
