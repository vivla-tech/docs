Los ficheros `.env` de tus repos. Tiene dos subcomandos:

- **`pull`** los vuelve a bajar de Vercel, Railway o la plantilla y **sobrescribe** tus valores con lo que llega. Úsalo cuando alguien añade o cambia una variable en la plataforma, o cuando tu `.env` se ha quedado viejo.
- **[`drift`](#vivla-env-drift)** compara qué variables hay en cada sitio (la plantilla, el entorno del que se bajan, producción y tu `.env`) y dice cuáles faltan dónde. Úsalo antes de desplegar algo que lee una variable nueva.

```bash
vivla env pull vivla-cms                # vuelve a bajar los .env de vivla-cms
vivla env pull vivla-cms vivla-api      # varios repos
vivla env pull vivla-tools --json       # NDJSON, para un agente
vivla env drift vivla-tools             # qué variables faltan dónde
```

Todo lo que sigue hasta [`vivla env drift`](#vivla-env-drift) es de `pull`.

## Opciones

`vivla env pull <repo>…` necesita al menos un repo del catálogo. No tiene opciones propias; de las globales, las que cuentan aquí:

| Opción             | Por defecto                | Qué hace                                                                     |
| ------------------ | -------------------------- | ---------------------------------------------------------------------------- |
| `--root <dir>`     | la guardada, si no `~/dev` | dónde están los clones (también `VIVLA_CLI_ROOT`; ver [`config`](/cli/commands/config)) |
| `--json`           |                            | NDJSON en stdout (ver [Salida `--json`](#salida---json))                     |
| `--manifest <dir>` |                            | un catálogo local, para probar fuentes nuevas antes de subirlas              |

`--force-env` va siempre puesto: es lo que distingue `pull` de la tarea `env` de un `setup`. Más opciones globales en [commands.md](/cli/commands/index#opciones-globales).

## Cómo funciona

`env pull` es un [`setup`](/cli/commands/setup) con `--only 'repo:<repo>:env'` para cada repo y `--force-env`. Como `--only` arrastra las dependencias, si el repo no está clonado lo clona, y si una fuente necesita un login (`login:vercel`, `login:railway`) lo comprueba antes. No abre la TUI: siempre es headless.

### Las fuentes

Cada repo declara sus fuentes en `env:` de su fichero del catálogo ([manifest.md](/cli/manifest#fuentes-de-env)), y se procesan en ese orden:

| Fuente    | Qué ejecuta                                                                                                                       | Qué se quita          |
| --------- | --------------------------------------------------------------------------------------------------------------------------------- | --------------------- |
| `vercel`  | `vercel env pull` a un fichero temporal, con el `environment` (por defecto `development`), el `project` y el `scope` de la fuente | `VERCEL` y `VERCEL_*` |
| `railway` | `railway link` del proyecto, entorno y servicio en la carpeta del `.env` y `railway variables --json`                             | `RAILWAY_*`           |
| `example` | lee la plantilla (`template`, o `<path>.example`). Si no existe, no aporta nada                                                   |                       |

Vercel y Railway inyectan esas variables para su propio runtime y en local solo estorban. El `railway link` queda apuntado en `~/.railway/config.json` por carpeta: no escribe nada dentro del repo. Si una fuente remota no devuelve ninguna variable, avisa: suele ser un proyecto o entorno mal escrito en el catálogo.

Las fuentes nunca son de producción. El catálogo solo apunta a entornos de desarrollo, preview, testing o staging, y un test (`test/manifest.test.ts`) falla si alguna fuente de Vercel o Railway dice `production`.

### Cómo se mezcla

Cada fuente se mezcla en su fichero (`path`), que se crea si no existe, con permisos `600`:

- Se conservan los comentarios, el orden y las líneas del fichero.
- Una clave nueva se añade al final, bajo un comentario que dice de dónde viene (`# from vercel (preview) via vivla`, `# from .env.example`).
- Una clave que ya tienes vacía se rellena siempre.
- Una clave que ya tienes con valor: en `env pull`, lo que llega de Vercel o Railway la sobrescribe; lo de la plantilla nunca. En un `setup` normal, sin `--force-env`, tu valor gana.
- Un valor vacío que llega nunca borra el tuyo.

Si dos fuentes escriben la misma clave en el mismo fichero, gana la última remota de la lista.

Al acabar se apunta la fecha en `~/.vivla/cli/state.json` (`repo:<repo>:env`) y avisa de las claves de la plantilla que siguen vacías, hasta 8 por fichero: esas no están en ninguna plataforma y te las tiene que pasar alguien.

### Con `--connect`

Si el repo se conecta a otros, `env pull` corre también su tarea `connect` después de bajar los `.env`, con el modo que le pases: `--connect remote` por defecto, `--connect local` o `--set connect.<repo>=local`. Así lo que llega de Vercel o Railway no deja una URL de servicio apuntando a otro sitio. Si montaste un servicio en local, vuelve a pasar `--connect local` en el `pull`.

## Qué toca

Escribe los `.env` de tus clones y `~/.vivla/cli/state.json`. Fuera, solo **lee**: variables de entornos de desarrollo o staging de Vercel y Railway.

## Salida `--json`

La de [`setup`](/cli/commands/setup#salida---json): `start`, los `task` y un `result`. La tarea que importa es `repo:<repo>:env`. Mientras corre, su `detail` dice qué fuente está bajando, y al acabar los avisos van en `notes` y en `result.next_actions` con `kind: warning`:

```json
{"type":"task","ts":1792753401200,"id":"repo:vivla-cms:env","title":"vivla-cms: .env files","repo":"vivla-cms","status":"running","detail":"apps/web/.env ← vercel (vivla-cms)"}
{"type":"task","ts":1792753404810,"id":"repo:vivla-cms:env","title":"vivla-cms: .env files","repo":"vivla-cms","status":"done","detail":"Done","notes":[{"kind":"warning","message":"vivla-cms/apps/web/.env: 1 variable(s) still empty: SOME_KEY"}],"duration":3610}
{"type":"result","ok":true,"status":"ok","exitCode":0,"counts":{"pending":0,"running":0,"done":1,"skipped":6,"failed":0,"blocked":0},"duration":5120,"tasks":[…],"next_actions":[{"task":"repo:vivla-cms:env","kind":"warning","message":"vivla-cms/apps/web/.env: 1 variable(s) still empty: SOME_KEY"}]}
```

## Exit codes

| Código | Cuándo                                                                                                 |
| ------ | ------------------------------------------------------------------------------------------------------ |
| `0`    | los `.env` están al día (los avisos de variables vacías no cambian el código)                          |
| `1`    | falló una fuente (por ejemplo `vercel env pull`), o un error inesperado                                |
| `4`    | falta un login (`vercel login`, `railway login`…) o el de GitHub para clonar: `next_actions[].command` |
| `64`   | un repo que no está en el catálogo                                                                     |

## `vivla env drift`

`vivla env drift [repo]`: por cada `.env` que baja el repo, qué variables faltan en algún sitio. Los sitios son la plantilla (`.env.example`), el entorno del que se baja (`railway develop`, `vercel preview`…), el mismo servicio en producción y tu `.env`. Así ves, antes de desplegar, que el código lee una variable que producción no tiene.

```bash
vivla env drift                  # el repo en el que estás
vivla env drift vivla-tools      # o uno por nombre
vivla env drift vivla-tools --json
```

```
vivla-tools · apps/backend/.env
  .env.example 98 · railway develop 104 · railway production 140 (names) · your .env 103
  ✖ OWNER_PORTAL_API_KEY            not in railway production
  ✖ SECONDARY_SLACK_ALLOWLIST       not in railway production
  ⚠ 38 only in production: AI_AGENT_DAILY_SUMMARY_ENABLED, BOOKING_WELCOME_ENABLED, …, +30 more
  · SLACK_SECONDARY_SIGNING_SECRET  not in your .env (vivla env pull)
  ~ your .env has other values than railway develop: CONCIERGE_API_KEY, VIVLA_API_ADMIN_M2M_SECRET

✖ 2 variable(s) the rest have are missing in production
```

No tiene opciones propias: el repo en el que estás o el que nombres, con su clon en `--root`.

### Cómo funciona

Por cada `path` de las fuentes `env:` del repo (y de sus `connect:`), lee:

| Sitio                              | De dónde                                                                                                                                                    | Qué se guarda             |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------- |
| la plantilla                       | el `template` (o `<path>.example`) en tu clon                                                                                                               | nombres                   |
| el entorno (`railway develop`…)    | Railway: `railway variables --json`. Vercel: `vercel env pull` a un fichero temporal, borrado al momento                                                    | nombre y hash de su valor |
| producción (`railway production`…) | Railway: `railway variables --json` del mismo servicio en su entorno de producción del catálogo (o `production`). Vercel: `vercel env ls production --json` | **solo nombres**          |
| tu `.env`                          | el fichero en tu clon                                                                                                                                       | nombre y hash de su valor |

**Producción nunca deja ver un valor.** La salida de Railway o Vercel pasa por un pequeño script de Node en la misma tubería del shell, que imprime solo los nombres. Los valores no llegan a este proceso ni a `~/.vivla/cli/vivla.log`. Con el entorno de desarrollo pasa lo mismo, pero el script imprime un hash corto (SHA-256, 16 caracteres) en vez del valor. Las comparaciones se hacen con esos hashes, y ningún valor ni hash sale en la salida. El hash no tiene en cuenta escapes ni espacios: una clave privada o un JSON de credenciales se lee igual en Railway que en el `.env` que escribió `setup`. Las variables que inyectan las plataformas (`VERCEL_*`, `RAILWAY_*`) no cuentan.

Con eso, cada variable que falta en algún sitio sale con un nivel:

| Nivel | Cuándo                                                                                                 |
| ----- | ------------------------------------------------------------------------------------------------------ |
| ✖     | está en la plantilla o en el entorno, y no en producción: si el código la lee, en producción no estará |
| ⚠     | solo está en producción, o el entorno de desarrollo no la tiene                                        |
| ·     | falta en la plantilla (`not in the template`) o en tu `.env` (`not in your .env`: `vivla env pull`)    |

Las variables que solo tienes tú en tu `.env` no cuentan. Si hay más de cuatro con el mismo aviso, van en una línea (con `--json` salen todas). Además:

- **`~`**: tu `.env` tiene otro valor que el entorno del que se baja. Las de `connect` no cuentan, porque esas las cambia `--connect` a propósito.
- **🔌**: para cada servicio conectado (`connect:`), si tu `.env` apunta al despliegue compartido, a tu clon local o a otra cosa, y si el entorno del repo apunta al mismo despliegue compartido que dice el catálogo.

Una fuente que no se puede leer (sin login, un entorno que no existe, el repo sin clonar) sale con `?` y su motivo, y el resto se compara sin ella.

### Qué toca

Solo lee, con tus sesiones de `railway` y `vercel`. Escribe el enlace de Railway en `~/.vivla/cli/railway/`, fuera de tus repos, y el fichero temporal de `vercel env pull` de desarrollo, que se borra en cuanto se lee. De producción solo pasan nombres.

### Salida `--json`

```json
{
  "type": "env-drift",
  "repo": "vivla-tools",
  "ok": false,
  "dir": "/Users/ana/dev/vivla-tools",
  "files": [
    {
      "path": "apps/backend/.env",
      "sources": [
        { "name": ".env.example", "kind": "template", "keys": 98 },
        { "name": "railway develop", "kind": "remote", "keys": 104 },
        { "name": "railway production", "kind": "production", "keys": 140 },
        { "name": "your .env", "kind": "local", "keys": 103 }
      ],
      "rows": [
        {
          "key": "OWNER_PORTAL_API_KEY",
          "present": [".env.example", "railway develop", "your .env"],
          "missing": ["railway production"],
          "level": "error",
          "note": "not in railway production"
        }
      ],
      "stale": [{ "key": "CONCIERGE_API_KEY", "source": "railway develop" }],
      "connect": []
    }
  ]
}
```

`ok` es `false` si alguna fila tiene `level: error`. En `connect`, `local` es `remote`, `local`, `other` o `missing`, y `source.matches` dice si el entorno apunta al mismo despliegue que el catálogo.

### Exit codes

| Código | Cuándo                                                                            |
| ------ | --------------------------------------------------------------------------------- |
| `0`    | producción tiene todo lo que tienen la plantilla y el entorno                     |
| `1`    | falta en producción alguna variable que el resto tiene                            |
| `64`   | un repo que no existe, o uno que no baja ningún `.env` (sin `env:` ni `connect:`) |

### Para agentes (MCP)

Tool `env_drift`, con `repo`. Devuelve el mismo objeto que `--json`, sin `type`.
