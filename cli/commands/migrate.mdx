Migraciones SQL al estilo de vivla-tools: ficheros numerados (`503_nombre.sql`) que se aplican a mano y quedan apuntados en una tabla de registro (`public.app_migrations`). `migrate` crea el siguiente fichero, revisa lo que puede salir mal en producción, dice cuáles faltan en un entorno y aplica uno, pidiendo confirmación en producción.

```bash
vivla migrate new "secondary market fees"        # crea 504_secondary_market_fees.sql
vivla migrate check                              # revisa las que añade tu rama
vivla migrate check 504 --try                    # y la prueba en dev, deshaciéndola
vivla migrate status                             # qué falta en dev
vivla migrate status --env prod                  # y en producción (solo lee)
vivla migrate apply 504                          # aplica en dev y la registra
vivla migrate apply 504 --env prod --notes "#1690"   # en producción: pide confirmación
```

Los subcomandos trabajan sobre el repo en el que estás, o el de `--repo`. El repo necesita `migrations` en el catálogo.

## `vivla migrate new`

`vivla migrate new <nombre> [--repo <repo>]`

| Opción          | Por defecto             | Qué hace                              |
| --------------- | ----------------------- | ------------------------------------- |
| `nombre`        |                         | lo que hace la migración, en palabras |
| `--repo <repo>` | el clon en el que estás | el repo del catálogo                  |

Crea `<N+1>_<nombre>.sql` en `migrations.dir`, donde `N` es el número más alto de la carpeta. El número se rellena con ceros al ancho del primer fichero (3 si no hay ninguno) y el nombre pasa a minúsculas, sin acentos y con `_`. El fichero trae una plantilla con `BEGIN;` y `COMMIT;`. Nunca sobrescribe: si ya existe un fichero con ese nombre, falla. No toca ninguna base de datos.

## `vivla migrate check`

`vivla migrate check [ficheros…] [--repo <repo>] [--try]`

| Opción           | Por defecto                                          | Qué hace                                                         |
| ---------------- | ---------------------------------------------------- | ---------------------------------------------------------------- |
| `ficheros…`      | los que añade tu rama; si no, los que faltan en prod | `504`, `504_nombre`, `504_nombre.sql` o la ruta a un `.sql`      |
| `--repo <repo>`  | el clon en el que estás                              | el repo del catálogo                                             |
| `--try`          | no                                                   | además, ejecuta cada una en la base de datos de dev y la deshace |
| `--yes` (global) | no                                                   | confirma `--try` sin preguntar                                   |

```
✖ 252_drop_unused_booking_flags.sql
  ✖   41  drop-column                  drops bookings_snapshot.flag_review and its data
                                       ALTER TABLE bookings_snapshot
⚠ 473_suppliers_iban.sql
  ⚠    1  no-transaction               a failure halfway leaves it half applied: wrap it in BEGIN; … COMMIT;
✔ 517_secondary_profiles_sales_cx.sql

3 file(s) · 1 error(s) · 1 warning(s) · 0 note(s)
  Meant it? Put `-- vivla-check: allow <rule>` right above that statement
```

**Qué ficheros.** Los que nombres. Si no nombras ninguno y estás en una rama que no es la base (`develop`), los `.sql` que tu rama añade en `migrations.dir` frente a `origin/<base>`, también los que aún no has commiteado. Si estás en la base, o tu rama no añade ninguno, los que el registro de producción no tiene (como `status --env prod`, que solo lee).

**Qué mira.** Lee el SQL sentencia a sentencia, sin parsearlo del todo: los textos entre comillas, los comentarios y los cuerpos `$$ … $$` (funciones, `DO`) no cuentan, así que un `DELETE` dentro de una función no salta. Lo que hace la propia migración también cuenta: borrar, rellenar o cambiar una tabla que el mismo fichero acaba de crear no avisa.

| Regla                         | Nivel   | Cuándo                                                                                                 |
| ----------------------------- | ------- | ------------------------------------------------------------------------------------------------------ |
| `drop-table`                  | error   | `DROP TABLE` de una tabla que el fichero no ha creado: se van sus filas                                |
| `drop-schema`                 | error   | `DROP SCHEMA`                                                                                          |
| `drop-column`                 | error   | `ALTER TABLE … DROP COLUMN`                                                                            |
| `truncate`                    | error   | `TRUNCATE`                                                                                             |
| `delete-all`                  | error   | `DELETE` sin `WHERE`                                                                                   |
| `not-null-no-default`         | error   | `ADD COLUMN … NOT NULL` sin `DEFAULT` en una tabla que ya existe: falla si tiene filas                 |
| `concurrently-in-transaction` | error   | `CREATE/DROP INDEX CONCURRENTLY` dentro de `BEGIN … COMMIT`: Postgres no lo deja                       |
| `update-all`                  | warning | `UPDATE` sin `WHERE`: bien para un backfill, revisa que lo sea                                         |
| `alter-type`                  | warning | `ALTER COLUMN … TYPE`: reescribe la tabla bloqueándola, y cada valor tiene que convertirse             |
| `set-not-null`                | warning | `ALTER COLUMN … SET NOT NULL`: recorre la tabla y falla si queda algún `NULL`                          |
| `rename`                      | warning | renombrar una tabla o columna: el código que aún use el nombre viejo falla hasta desplegar             |
| `no-transaction`              | warning | varias sentencias sin `BEGIN … COMMIT`: si una falla, queda a medias                                   |
| `index-lock`                  | nota    | `CREATE INDEX` sin `CONCURRENTLY` en una tabla que ya existe: bloquea escrituras mientras se construye |
| `not-idempotent`              | nota    | `CREATE`/`ADD COLUMN` sin `IF NOT EXISTS`, `DROP` sin `IF EXISTS`: aplicarla dos veces falla           |

Los errores hacen que termine con `exit 1`; los warnings y las notas, no. Si lo que avisa es justo lo que quieres (borrar una columna que nadie lee), pon un comentario justo encima de esa sentencia:

```sql
-- Nadie lee estos flags desde #1240
-- vivla-check: allow drop-column
ALTER TABLE bookings DROP COLUMN IF EXISTS flag_review;
```

Vale para esa sentencia y nada más. Se pueden poner varias reglas separadas por comas, o `all`.

**`--try`.** Después de revisarlas, ejecuta cada fichero en el proyecto `dev` de Supabase (nunca en otro) dentro de una transacción que se deshace: quita el `BEGIN;` y el `COMMIT;` del fichero, lo envuelve en `BEGIN; … ROLLBACK;` y, al final, comprueba que la transacción se deshizo de verdad. Dice si se aplicaría limpio contra el esquema de dev de ahora, o el error con el que falla. Antes pregunta, porque mientras corre bloquea las tablas que toque (sin terminal: `--yes`). No ejecuta ficheros que no caben en una transacción (`CONCURRENTLY`, `VACUUM`, sus propios `COMMIT`). Si la migración ya está aplicada en dev, lo normal es que falle o no diga nada nuevo.

## `vivla migrate status`

`vivla migrate status [--repo <repo>] [--env <env>]`

| Opción          | Por defecto             | Qué hace                                            |
| --------------- | ----------------------- | --------------------------------------------------- |
| `--repo <repo>` | el clon en el que estás | el repo del catálogo                                |
| `--env <env>`   | `dev`                   | el entorno: una clave de `supabase` (`dev`, `prod`) |

Lee la tabla de registro del entorno (`select filename, applied_by, applied_at … order by applied_at desc`) y la compara con la carpeta:

- Enseña las 5 últimas registradas, con quién y cuándo.
- Lista como pendientes (`○`) los ficheros que no están en el registro, pero solo desde el número más bajo que sí está: lo anterior es de antes de que existiera el registro y no se juzga. Si el registro está vacío, no marca ninguno.
- En pantalla salen como mucho los 10 últimos pendientes; `--json` los da todos.

Necesita `migrations.registry`. Solo lee, también en producción.

## `vivla migrate apply`

`vivla migrate apply <fichero> [--repo <repo>] [--env <env>] [--notes <texto>] [--force]`

| Opción            | Por defecto             | Qué hace                                               |
| ----------------- | ----------------------- | ------------------------------------------------------ |
| `fichero`         |                         | `504`, `504_nombre` o `504_nombre.sql`                 |
| `--repo <repo>`   | el clon en el que estás | el repo del catálogo                                   |
| `--env <env>`     | `dev`                   | el entorno: una clave de `supabase`                    |
| `--notes <texto>` | vacío                   | nota que se guarda en el registro (el PR, por ejemplo) |
| `--force`         | no                      | la aplica aunque el registro diga que ya está          |
| `--yes` (global)  | no                      | confirma en producción sin preguntar                   |

1. Busca el fichero en `migrations.dir`.
2. Si hay registro y no pasas `--force`, mira si ya está aplicado. Si lo está, lo dice y termina sin hacer nada.
3. En producción (`prod` o `production`) pide confirmación: `Apply 504_… to vivla-tools PRODUCTION (<ref>)? [y/N]` (vale `y`, `yes`, `s`, `si`, `sí`). Sin terminal, o con `--json`, no pregunta: termina con `exit 4` y el comando con `--yes` en `next_actions`.
4. Ejecuta el fichero entero en Supabase (`supabase db query --linked -f`).
5. Lo apunta en el registro: `filename`, `applied_by` (tu `git config user.name` seguido de ` (vivla)`) y `notes`.

En dev aplica sin preguntar.

## Cómo funciona

Las consultas van por la Management API de Supabase con `supabase db query --linked`: no hace falta la contraseña de la base de datos, solo `supabase login`. El `supabase link` de cada proyecto se hace en `~/.vivla/cli/supabase/<ref>`, nunca dentro de tu repo. La carpeta de migraciones se lee del clon en el que estás o de `~/dev/<repo>`.

## Qué toca

| Subcomando | Toca                                                                                                                                          |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `new`      | local: crea un fichero en tu clon                                                                                                             |
| `check`    | local: lee los ficheros. Sin ficheros y en la base, lee el registro de producción. Con `--try`, ejecuta en dev y lo deshace, con confirmación |
| `status`   | lee la tabla de registro del entorno                                                                                                          |
| `apply`    | escribe en la base de datos del entorno. En producción, solo con confirmación o `--yes`                                                       |

`--yes` en producción solo después de que una persona haya aprobado esa migración en concreto.

## Salida `--json`

`new`:

```json
{
  "type": "migration",
  "file": "apps/backend/src/database/migrations/504_secondary_market_fees.sql"
}
```

`check`:

```json
{
  "type": "migrate-check",
  "ok": false,
  "source": "branch",
  "detail": "new on feat/drop-flags against develop",
  "files": [
    {
      "file": "252_drop_unused_booking_flags.sql",
      "findings": [
        {
          "rule": "drop-column",
          "severity": "error",
          "line": 41,
          "message": "drops bookings_snapshot.flag_review and its data",
          "statement": "ALTER TABLE bookings_snapshot"
        }
      ],
      "try": { "ok": true }
    }
  ]
}
```

`source` dice de dónde salen los ficheros: `named`, `branch`, `unapplied` (los que faltan en producción) o `none`. `try` solo aparece con `--try`: `{ "ok": false, "error": "…" }` con el error de Postgres si falla en dev.

`status`:

```json
{
  "type": "migrations",
  "env": "dev",
  "registry": "public.app_migrations",
  "unrecorded": ["504_secondary_market_fees.sql"],
  "latest": [
    {
      "filename": "503_secondary_market_transactions.sql",
      "applied_by": "Ana Pérez (vivla)",
      "applied_at": "2026-10-22T09:12:03.000Z"
    }
  ]
}
```

`apply`:

```json
{ "type": "migration", "file": "504_secondary_market_fees.sql", "env": "dev", "applied": true }
{ "type": "migration", "file": "504_secondary_market_fees.sql", "env": "dev", "applied": false, "message": "already applied" }
```

En producción sin `--yes`:

```json
{
  "type": "result",
  "ok": false,
  "status": "blocked",
  "exitCode": 4,
  "message": "Apply 504_secondary_market_fees.sql to vivla-tools PRODUCTION (<ref>)? Needs confirmation.",
  "next_actions": [
    {
      "kind": "human",
      "message": "Apply 504_secondary_market_fees.sql to vivla-tools PRODUCTION (<ref>)?",
      "command": "vivla migrate apply 504_secondary_market_fees.sql --env prod --yes"
    }
  ]
}
```

## Exit codes

| Código | Cuándo                                                                                                |
| ------ | ----------------------------------------------------------------------------------------------------- |
| `0`    | creada, consultada, aplicada, ya estaba aplicada, o `check` sin errores                               |
| `1`    | falló el SQL o Supabase, `check` encontró errores o `--try` falló en dev, o respondiste que no        |
| `4`    | producción (o `check --try`) sin `--yes` y sin nadie que confirme                                     |
| `64`   | repo sin `migrations` (o sin `registry` para `status`), entorno sin `supabase`, fichero que no existe |

## Para agentes (MCP)

La tool `migrations` es el `status` resumido: entradas `repo` (por defecto `vivla-tools`) y `env` (`dev`); devuelve `{ env, latest }` con las 10 últimas registradas.

La tool `migrate_check` es `check` sin `--try`: entradas `repo` y `files` (vacío: los de por defecto); devuelve `{ ok, source, detail, files }` como arriba. Nunca ejecuta SQL. Un agente que escribe una migración debería pasarla por aquí antes de proponerla.

`new`, `apply` y `check --try` no son tools: un agente aplica por la CLI (`vivla migrate apply <fichero> --env <env> --json`), y en producción solo con `--yes` después de que una persona lo apruebe.
