# Builds

La app de Vivla utiliza **EAS Build** (Expo Application Services) para generar los binarios de iOS y Android. Todos los perfiles de build estan definidos en `eas.json`.

<Note>
  Se requiere **EAS CLI version 16.16.0** o superior. Instalalo con `npm install -g eas-cli`.
</Note>

## Perfiles de build

El proyecto define cinco perfiles de build, cada uno orientado a una etapa distinta del ciclo de desarrollo:

| Perfil           | Distribucion | Canal       | Entorno     | Android    | iOS       | Uso                            |
| ---------------- | ------------ | ----------- | ----------- | ---------- | --------- | ------------------------------ |
| `development`    | internal     | development | development | APK        | Simulador | Desarrollo local               |
| `preview`        | store        | develop     | development | App Bundle | Release   | Testing interno / TestFlight   |
| `beta-prod`      | store        | beta-prod   | production  | APK        | Release   | QA con API de produccion       |
| `beta-prod-play` | store        | beta-prod   | production  | App Bundle | —         | Mismo build, para subir a Play |
| `production`     | store        | production  | production  | App Bundle | Release   | Publicacion en stores          |

`beta-prod-play` hereda de `beta-prod` (`extends`) y solo cambia el formato del artefacto de Android.
Existe porque los dos destinos piden cosas distintas: la instalacion directa en un movil necesita un
**APK**, y Google Play solo acepta **App Bundle** en fichas creadas de 2021 en adelante. Para iOS no
aporta nada — usa `beta-prod`.

## Configuracion por plataforma

<Tabs>
  <Tab title="iOS">
    - **Imagen de build**: `sdk-54` en todos los perfiles. Esta imagen incluye **Xcode 26** y compila
    con **iOS 26 SDK**, requerido por App Store Connect a partir del 28 de abril de 2026. -
    **Credenciales**: gestionadas de forma remota por EAS (no se almacenan localmente) - **Build
    configuration**: `Release` - **New Architecture**: habilitada. Los provisioning profiles y
    certificados se manejan automaticamente.
  </Tab>
  <Tab title="Android">
    - **Hermes**: habilitado como motor de JavaScript - **ProGuard**: deshabilitado - **New
    Architecture**: habilitada - El keystore se gestiona de forma remota por EAS

    <Note>
      Flipper fue eliminado en React Native 0.80+. La configuración explícita de `flipper: false` ya
      no es necesaria en `expo-build-properties`.
    </Note>

  </Tab>
</Tabs>

## Imagen de build de iOS (Xcode 26)

A partir de la actualización a Expo SDK 54, todos los perfiles de iOS en `eas.json` declaran explícitamente la imagen `"image": "sdk-54"`:

<CodeGroup>
```json eas.json (fragmento)
{
  "build": {
    "preview": {
      "ios": {
        "image": "sdk-54",
        "simulator": false,
        "buildConfiguration": "Release"
      }
    }
  }
}
```
</CodeGroup>

Esta imagen incluye:

- **macOS Sequoia 15.6**
- **Xcode 26**
- **iOS 26 SDK**

<Warning>
  Apple requiere que todas las apps subidas a App Store Connect a partir del **28 de abril de 2026**
  sean compiladas con iOS 26 SDK (Xcode 26). Builds más antiguos serán rechazados.
</Warning>

## Scripts de build

Usa los siguientes scripts de npm para ejecutar builds desde la terminal:

<CodeGroup>
```bash Desarrollo
npm run build:development
```

```bash Preview
npm run build:preview
```

```bash Produccion
npm run build:production
```

```bash Enviar a stores
npm run submit:production
```

</CodeGroup>

| Script                      | Descripcion                                            |
| --------------------------- | ------------------------------------------------------ |
| `npm run build:development` | Build de desarrollo para testing local                 |
| `npm run build:preview`     | Build preview para testing interno y TestFlight        |
| `npm run build:production`  | Build de produccion para publicacion en stores         |
| `npm run submit:production` | Envia el build de produccion a App Store y Google Play |

## Iconos por entorno

Cada entorno utiliza un icono diferente para facilitar la identificacion de la app instalada en el dispositivo:

| Entorno                   | iOS                    | Android (foreground adaptativo)    | Fondo     |
| ------------------------- | ---------------------- | ---------------------------------- | --------- |
| `development` / `develop` | `vivla_dev_icon.png`   | `android_adaptive_development.png` | `#D78C3F` |
| `beta-prod`               | `vivla_stage_icon.png` | `android_adaptive_staging.png`     | `#745888` |
| `production`              | `ios_icon.png`         | `android_adaptive_production.png`  | `#0A0A0A` |

Android enmascara el icono a circulo o squircle y solo garantiza el **66% central** de un lienzo de
108x108dp. Por eso los assets de Android son distintos de los de iOS: llevan el sol con alfa real al
54% del lienzo, y el color de entorno va en la capa de fondo (`adaptiveIcon.backgroundColor`), no
horneado en el PNG. Reutilizar el icono de iOS recorta las puntas del logo.

## Bundle IDs

Los identificadores varian segun el entorno para permitir la instalacion simultanea de varias
versiones. **Son los mismos en iOS y Android**: cualquier asimetria rompe la distribucion (ver aviso
abajo).

| Entorno     | iOS y Android                 |
| ----------- | ----------------------------- |
| Development | `com.vivla.booking.beta`      |
| Beta Prod   | `com.vivla.booking.beta.prod` |
| Production  | `com.vivla.app`               |

<Warning>
  Hasta agosto de 2026, `beta-prod` usaba `com.vivla.app` en Android — el mismo que produccion. El
  APK no se podia instalar en un movil con la app publicada (mismo package, firma distinta: Play App
  Signing frente al keystore de EAS), beta y produccion no podian convivir, y subirlo a Play habria
  publicado sobre la ficha de produccion. Si alguna vez hay que tocar un identificador, cambiarlo en
  **ambas plataformas** a la vez.
</Warning>

<Note>
  Cada package de Android necesita su cliente en `google-services.json`, o el build falla con "No
  matching client found for package name". El fichero se regenera desde Firebase (proyecto
  `vivla-app`): `firebase apps:sdkconfig ANDROID <appId> --project vivla-app`. Al anadir un entorno
  nuevo hay que crear antes la app: `firebase apps:create android "<nombre>" --package-name <package>
  --project vivla-app`.
</Note>

## Distribucion a testers

<Tabs>
  <Tab title="iOS — TestFlight">
    ```bash
    eas build --profile beta-prod --platform ios
    eas submit --profile beta-prod --platform ios --latest
    ```

    Sube al app record de beta (`6751716725`), distinto del de produccion. Apple procesa el binario
    en 5-10 minutos y avisa por correo.

  </Tab>

  <Tab title="Android — instalacion directa">
    ```bash
    eas build --profile beta-prod --platform android
    ```

    Genera un **APK** con enlace de descarga. El tester lo abre en su movil y acepta instalar de
    origenes desconocidos. No necesita cuenta de Google Play. Es la via rapida para pocos testers.

  </Tab>

  <Tab title="Android — Google Play">
    ```bash
    eas build --profile beta-prod-play --platform android
    eas submit --profile beta-prod-play --platform android --latest
    ```

    Sube un **App Bundle** al track `internal` en estado borrador. Requisitos previos, que solo hacen
    falta la primera vez:

    1. Crear la ficha en Play Console con el package `com.vivla.booking.beta.prod` — es una **app
       nueva**, no hereda nada de la de produccion.
    2. Completar el cuestionario de contenido y la ficha minima que Play exige antes de aceptar
       ninguna subida.
    3. Dar de alta a los testers por correo en el track interno.

    El `versionCode` debe ir siempre por delante del ultimo subido a esa ficha.

  </Tab>
</Tabs>

<Note>Antes de hacer build, siempre ejecutar `npm run validate` para verificar lint y tests.</Note>

<Warning>
  Los builds de produccion consumen creditos de EAS. Usa `development` o `preview` para pruebas y
  reserva `production` para releases finales.
</Warning>
